# Requirements Document

## Introduction

This document defines the requirements for integrating the React frontend with the Strapi 5 backend in the University Ambassadors CMS. The integration layer provides a typed API client, authentication via Strapi users-permissions, role-based data access, and standardized error/loading state handling. The system supports multiple user roles (Student, Ambassador, Professor) with distinct permissions: students can create clubs and events, ambassadors approve club and event creation, and club owners manage club events. The frontend currently has no API layer, routing, or state management — this feature establishes the foundation for all future data-driven UI work.

## Glossary

- **API_Client**: A configured HTTP client instance (using fetch or axios) responsible for making requests to the Strapi REST API, including base URL configuration, header management, and request/response interceptors.
- **Auth_Service**: The module responsible for user authentication operations (login, registration, logout) using the Strapi users-permissions plugin endpoints.
- **Token_Store**: The mechanism for persisting and retrieving the JWT token received from Strapi authentication, stored in browser localStorage.
- **Strapi_REST_API**: The REST API automatically generated by Strapi 5 for each content type, available at `http://localhost:1337/api/{plural-name}`.
- **Content_Service**: A typed service module that wraps API_Client calls for a specific Strapi content type, providing CRUD operations with proper TypeScript generics.
- **API_Response**: The standard Strapi 5 response envelope containing `data` (single object or array with `id` and `attributes`) and optional `meta` (pagination info).
- **API_Error**: A structured error object returned by the API_Client when a request fails, containing status code, error message, and optional validation details.
- **Request_State**: An object representing the current state of an async API operation, containing `data`, `isLoading`, `error`, and `isSuccess` fields.
- **Student_Role**: A user with an associated Student_Profile who can create Activity Clubs and Events (subject to ambassador approval).
- **Ambassador_Role**: A user with an associated Ambassador_Profile who can approve or deny club creation requests and event creation requests.
- **Club_Owner_Role**: A user who is the owner of an Activity Club (the `users_permissions_user` relation on the club) and can create events associated with that club.
- **Approval_Status**: A status field that tracks whether a created entity (club or event) is pending approval, approved, or denied.

## Requirements

### Requirement 1: API Client Configuration

**User Story:** As a frontend developer, I want a centralized API client configured for the Strapi backend, so that all HTTP requests use consistent settings and I can change the base URL in one place.

#### Acceptance Criteria

1. THE API_Client SHALL use a base URL configured via an environment variable `VITE_STRAPI_URL` defaulting to `http://localhost:1337`.
2. THE API_Client SHALL prepend the base URL followed by `/api` to all request paths sent to the Strapi backend, including both content-type endpoints and authentication endpoints.
3. WHEN a request contains a body, THE API_Client SHALL set the `Content-Type` header to `application/json`.
4. WHEN a JWT token exists in the Token_Store, THE API_Client SHALL include an `Authorization: Bearer <token>` header on every request.
5. WHEN no JWT token exists in the Token_Store, THE API_Client SHALL send requests without the Authorization header.
6. THE API_Client SHALL enforce a request timeout of 30 seconds, after which the request is aborted and treated as a network error.

### Requirement 2: Authentication - Login

**User Story:** As a user, I want to log in with my email and password, so that I can access protected content and perform actions tied to my account.

#### Acceptance Criteria

1. WHEN a user submits credentials, THE Auth_Service SHALL send a POST request to `/api/auth/local` with `identifier` (non-empty string, maximum 254 characters) and `password` (non-empty string, maximum 128 characters) fields.
2. WHEN the Strapi_REST_API returns a 200 status with a response body containing `jwt` and `user` fields, THE Auth_Service SHALL store the `jwt` value in the Token_Store before returning the result.
3. WHEN the Strapi_REST_API returns a 200 status with a valid authentication response, THE Auth_Service SHALL return the authenticated user object including `id`, `username`, and `email` fields extracted from the response `user` object.
4. IF the Strapi_REST_API returns a 400 status for invalid credentials, THEN THE Auth_Service SHALL return an API_Error containing the HTTP status code and the error message from the server response body.
5. IF the Strapi_REST_API does not respond within 30 seconds or a network error occurs, THEN THE Auth_Service SHALL return an API_Error with status code 0 and a message indicating a network connectivity failure.
6. IF the Strapi_REST_API returns a 200 status but the response body does not contain the expected `jwt` or `user` fields, THEN THE Auth_Service SHALL return an API_Error with a message indicating an unexpected response format.

### Requirement 3: Authentication - Registration

**User Story:** As a new user, I want to register an account, so that I can start using the ambassadors platform.

#### Acceptance Criteria

1. WHEN a user submits registration data, THE Auth_Service SHALL send a POST request to `/api/auth/local/register` with `username` (3 to 50 characters), `email` (valid email format), and `password` (minimum 6 characters) fields.
2. WHEN the Strapi_REST_API returns a successful registration response, THE Auth_Service SHALL store the JWT token in the Token_Store.
3. WHEN the Strapi_REST_API returns a successful registration response, THE Auth_Service SHALL return the newly created user object including `id`, `username`, and `email`.
4. IF the Strapi_REST_API returns a 400 status for registration validation errors (duplicate email, duplicate username, missing required fields, or invalid field format), THEN THE Auth_Service SHALL return an API_Error with the validation message from the server response.
5. IF the Strapi_REST_API is unreachable or the request times out after 30 seconds, THEN THE Auth_Service SHALL return an API_Error with status code 0 and a descriptive network error message.

### Requirement 4: Authentication - Session Management

**User Story:** As a logged-in user, I want my session to persist across page reloads and I want to be able to log out, so that I have a seamless and secure experience.

#### Acceptance Criteria

1. WHEN the application initializes, THE Auth_Service SHALL check the Token_Store for an existing JWT token.
2. WHEN a JWT token exists in the Token_Store at initialization, THE Auth_Service SHALL send a GET request to `/api/users/me` to retrieve the current user profile and, upon a successful response, set the authentication state to authenticated with the returned user object.
3. IF the `/api/users/me` request returns a 401 status, THEN THE Auth_Service SHALL remove the token from the Token_Store and set the authentication state to unauthenticated.
4. IF the `/api/users/me` request fails due to a network error or a non-401 error status, THEN THE Auth_Service SHALL remove the token from the Token_Store and set the authentication state to unauthenticated.
5. IF no JWT token exists in the Token_Store at initialization, THEN THE Auth_Service SHALL set the authentication state to unauthenticated without making any network requests.
6. WHEN the user requests logout, THE Auth_Service SHALL remove the JWT token from the Token_Store.
7. WHEN the user requests logout, THE Auth_Service SHALL clear the cached user object from application state and set the authentication state to unauthenticated.

### Requirement 5: TypeScript Types for Content Types

**User Story:** As a frontend developer, I want TypeScript interfaces matching all Strapi content types, so that I get compile-time type safety when working with API data.

#### Acceptance Criteria

1. THE Frontend SHALL define TypeScript interfaces for all content types: Campus, Building, Location, Event, EventAttendee, ActivityClub, ClubMembership, AmbassadorProfile, StudentProfile, ProfessorProfile, NewsArticle, and Issue, where each interface includes all scalar (non-relation) attributes defined in the corresponding Strapi schema with mapped TypeScript types (string fields as `string`, integer/biginteger fields as `number`, datetime fields as `string`, boolean fields as `boolean`, blocks fields as a dedicated block content type or `unknown`, and enumeration fields as their corresponding enum type).
2. THE Frontend SHALL define TypeScript string union types for all enumeration fields matching the exact values defined in the Strapi schemas: EventStatus (`"Pending Approval" | "Scheduled" | "Denied" | "Canceled" | "In Progress" | "Finished" | "Archived"`), LocationType, Priority, FocusArea, MemberRole, Department, and ProfessorTitle.
3. THE Frontend SHALL define a generic `StrapiResponse<T>` type representing the Strapi 5 response envelope where `data` is typed as `T` for single-entity responses or `T[]` for collection responses, and `meta` includes a `pagination` object with `page`, `pageSize`, `pageCount`, and `total` fields typed as numbers.
4. THE Frontend SHALL define a generic `StrapiEntity<T>` type that includes `id` typed as `number`, `documentId` typed as `string`, and the entity attributes spread at the same level (flat structure matching Strapi 5 response format).
5. THE Frontend SHALL define relation fields as optional properties where to-one relations (manyToOne, oneToOne) are typed as the related `StrapiEntity` or `null`, and to-many relations (oneToMany, manyToMany) are typed as an array of the related `StrapiEntity`.

### Requirement 6: Content Type Data Fetching

**User Story:** As a frontend developer, I want typed service functions for fetching content from all Strapi endpoints, so that I can retrieve and display data with proper type inference.

#### Acceptance Criteria

1. THE Content_Service SHALL be instantiated with a content-type plural API name (e.g., `"activity-clubs"`, `"events"`) and use it to construct request URLs relative to the API_Client base path.
2. THE Content_Service SHALL provide a `getMany<T>` function that sends a GET request to the collection endpoint and returns the `data` array from the Strapi response envelope typed as `StrapiEntity<T>[]`, along with the `meta.pagination` object.
3. THE Content_Service SHALL provide a `getOne<T>` function that sends a GET request to the single-entity endpoint by `documentId` and returns the `data` object from the Strapi response envelope typed as `StrapiEntity<T>`.
4. WHEN the caller passes query parameters (filters, sort, pagination, populate), THE Content_Service SHALL serialize them into Strapi 5 query string format using `qs` library with `encodeValuesOnly` option.
5. THE Content_Service SHALL provide a `create<T>` function that sends a POST request with the entity data wrapped in a `{ data: T }` body and returns the created entity unwrapped from the Strapi response envelope.
6. THE Content_Service SHALL provide an `update<T>` function that sends a PUT request to the entity endpoint by `documentId` with updated data wrapped in a `{ data: Partial<T> }` body and returns the updated entity unwrapped from the Strapi response envelope.
7. THE Content_Service SHALL provide a `delete` function that sends a DELETE request to the entity endpoint by `documentId` and returns void upon successful completion.
8. IF the API_Client returns an API_Error for any Content_Service operation, THEN THE Content_Service SHALL propagate the API_Error to the caller without modification.

### Requirement 7: Error Handling

**User Story:** As a frontend developer, I want consistent error handling across all API calls, so that I can display meaningful feedback to users and debug issues efficiently.

#### Acceptance Criteria

1. WHEN the Strapi_REST_API returns a 4xx or 5xx status, THE API_Client SHALL parse the error response body and construct a structured API_Error object.
2. THE API_Error SHALL contain the HTTP status code, an error name string (from the Strapi error response `error.name` field), and a non-empty message string (from the Strapi error response `error.message` field).
3. IF the Strapi_REST_API returns validation errors (status 400) and the response body contains an `error.details.errors` array, THEN THE API_Error SHALL include the field-level validation details as an array of objects each containing the field path and the validation message.
4. IF a network error occurs (server unreachable or request exceeds 30 seconds timeout), THEN THE API_Client SHALL return an API_Error with status code 0 and a message indicating the nature of the failure (timeout or connection refused).
5. WHEN the Strapi_REST_API returns a 401 status on any endpoint other than `/api/auth/local` and `/api/auth/local/register`, THE API_Client SHALL remove the token from the Token_Store and update the authentication state to unauthenticated.
6. IF the Strapi_REST_API returns a non-JSON response body on a 4xx or 5xx status, THEN THE API_Client SHALL construct an API_Error with the HTTP status code, error name set to "UnknownError", and a message indicating that the server returned an unexpected response format.

### Requirement 8: Request State Management

**User Story:** As a frontend developer, I want a standardized way to track loading, success, and error states for API calls, so that I can build consistent UI feedback patterns.

#### Acceptance Criteria

1. THE Frontend SHALL provide a custom React hook `useApiQuery` that accepts a fetcher function (a zero-argument function returning a Promise of the expected data type) and returns a Request_State object with `data`, `isLoading`, `error`, `isSuccess`, and a `refetch` function.
2. WHEN `useApiQuery` is first mounted, THE hook SHALL initialize state with `data` set to null, `isLoading` set to true, `error` set to null, and `isSuccess` set to false, and immediately invoke the fetcher function.
3. WHEN the API call completes successfully, THE hook SHALL set `data` to the response payload, `isLoading` to false, and `isSuccess` to true.
4. IF the API call fails, THEN THE hook SHALL set `error` to the API_Error object, `isLoading` to false, and `isSuccess` to false, while preserving any previously loaded `data` value.
5. WHEN the `refetch` function is called, THE hook SHALL set `isLoading` to true, `error` to null, and invoke the fetcher function again.
6. THE Frontend SHALL provide a custom React hook `useApiMutation` that accepts a mutation function (a function receiving a single argument of the request data type and returning a Promise of the response type) and returns an object containing a `mutate` function (accepting the request data and returning a Promise of the response), a `reset` function that restores the state to its initial values, and a Request_State object.
7. WHEN the `mutate` function is called, THE hook SHALL set `isLoading` to true and `error` to null before invoking the mutation function with the provided argument.
8. WHEN a component unmounts before an API call completes, THE hooks SHALL prevent state updates to the unmounted component.

### Requirement 9: Authentication Context

**User Story:** As a frontend developer, I want a React context that provides the current authentication state to any component in the tree, so that I can conditionally render UI based on login status.

#### Acceptance Criteria

1. THE Frontend SHALL provide an `AuthProvider` component that wraps the application and manages authentication state.
2. THE AuthProvider SHALL expose the current user object (or null if unauthenticated), `isAuthenticated` boolean, `isLoading` boolean, `error` (API_Error or null), and `login`, `register`, `logout` functions via React context, accessible through a `useAuth()` hook.
3. WHEN login or register succeeds, THE AuthProvider SHALL update the user state, set `isAuthenticated` to true, and set `error` to null.
4. WHEN logout is called, THE AuthProvider SHALL clear the user state, set `isAuthenticated` to false, and set `error` to null.
5. WHEN the application mounts, THE AuthProvider SHALL attempt to restore the session from the Token_Store and set `isLoading` to true until the session check resolves or fails, at which point `isLoading` SHALL be set to false regardless of the outcome.
6. IF login or register fails, THEN THE AuthProvider SHALL set `error` to the API_Error returned by the Auth_Service, keep `isAuthenticated` as false, and keep the user state as null.
7. IF session restoration fails due to an expired or invalid token (401 response), THEN THE AuthProvider SHALL clear the Token_Store, set `isAuthenticated` to false, set the user state to null, and set `isLoading` to false.
8. IF a component calls `useAuth()` outside of an `AuthProvider`, THEN THE hook SHALL throw an error indicating that it must be used within an AuthProvider.

### Requirement 10: Role-Based User Profile Fetching

**User Story:** As a logged-in user, I want the application to determine my role (Student, Ambassador, Professor) after login, so that I see the correct UI and permissions for my role.

#### Acceptance Criteria

1. WHEN authentication succeeds, THE Auth_Service SHALL fetch the user's associated profile by querying `/api/users/me` with `populate` parameter including `student_profile`, `ambassador_profile`, and `professor_profile` relations.
2. WHEN the populated user response contains a non-null `ambassador_profile` relation, THE AuthProvider SHALL expose the user's role as "ambassador" in the authentication context, regardless of other associated profiles.
3. WHEN the populated user response contains a non-null `student_profile` relation and a null `ambassador_profile` relation, THE AuthProvider SHALL expose the user's role as "student" in the authentication context.
4. WHEN the populated user response contains a non-null `professor_profile` relation and a null `ambassador_profile` relation and a null `student_profile` relation, THE AuthProvider SHALL expose the user's role as "professor" in the authentication context.
5. WHEN the populated user response contains both a non-null `student_profile` and a non-null `professor_profile` relation (and a null `ambassador_profile`), THE AuthProvider SHALL expose the user's role as "student" in the authentication context.
6. IF the populated user response contains null values for all three profile relations (`student_profile`, `ambassador_profile`, and `professor_profile`), THEN THE AuthProvider SHALL expose the user's role as null and set `isAuthenticated` to true with no role-specific permissions.
7. IF the profile fetch request to `/api/users/me` fails due to a network error or returns a non-401 error status, THEN THE Auth_Service SHALL retry the request once, and if it fails again, SHALL set the authentication state to authenticated with role as null and expose an API_Error indicating the profile could not be loaded.
8. THE AuthProvider SHALL expose the role as one of the string literal values "student", "ambassador", "professor", or null, alongside the role-specific profile data (StudentProfile, AmbassadorProfile, or ProfessorProfile, or null) in the authentication context next to the base user object.

### Requirement 11: Club Creation by Students

**User Story:** As a student, I want to create an activity club, so that I can organize activities and recruit members.

#### Acceptance Criteria

1. WHEN a user with Student_Role submits club creation data, THE Content_Service SHALL send a POST request to `/api/activity-clubs` with the club `name` (required, maximum 255 characters), `description` (optional), and the current user's ID as the `users_permissions_user` relation (owner).
2. WHEN the Strapi_REST_API returns a successful creation response, THE Content_Service SHALL return the created club entity and the club SHALL have its publication state set to draft (unpublished), indicating it requires ambassador approval.
3. IF the Strapi_REST_API returns a 400 status due to a duplicate club name or missing required field, THEN THE Content_Service SHALL return an API_Error containing the validation message from the server response.
4. IF the user does not have Student_Role or Ambassador_Role, THEN THE Frontend SHALL hide the club creation action from the UI so that it is not visible or interactive.
5. WHEN a club is successfully created, THE Frontend SHALL display a confirmation message indicating the club was created and is pending ambassador approval.

### Requirement 12: Club Approval by Ambassadors

**User Story:** As an ambassador, I want to review and approve or deny club creation requests, so that I can ensure clubs meet university standards.

#### Acceptance Criteria

1. WHEN a user with Ambassador_Role requests the list of pending clubs, THE Content_Service SHALL fetch activity clubs filtered by `publicationState=preview` (draft status) from the Strapi_REST_API, populating the `users_permissions_user` relation so the club creator's username is included in the response.
2. WHEN an ambassador approves a club, THE Content_Service SHALL send a publish action request to the Strapi_REST_API for that club's `documentId`, transitioning it from draft to published state.
3. WHEN an ambassador denies a club, THE Content_Service SHALL send a DELETE request to the Strapi_REST_API for that club's `documentId`, permanently removing the draft entry.
4. IF the user does not have Ambassador_Role, THEN THE Frontend SHALL not display the club approval interface and SHALL not expose approval or denial actions.
5. IF the Strapi_REST_API returns a 4xx or 5xx status when an ambassador attempts to approve or deny a club, THEN THE Content_Service SHALL return an API_Error and THE Frontend SHALL display an error message indicating the action failed without modifying the pending clubs list.

### Requirement 13: Event Creation by Students and Club Owners

**User Story:** As a student or club owner, I want to create events, so that I can organize gatherings for the university community.

#### Acceptance Criteria

1. WHEN a user with Student_Role submits event creation data, THE Content_Service SHALL send a POST request to `/api/events` with the required fields `title` (string, maximum 255 characters), `starts_at` (datetime), and `ends_at` (datetime), the current user as `creator`, and optionally `description` (blocks content) and `location` (relation to a Location entity).
2. WHEN an event is created by a Student_Role user, THE Content_Service SHALL set the initial `event_status` to "Pending Approval".
3. WHEN a Club_Owner_Role user creates an event for their club, THE Content_Service SHALL associate the event with the activity club via the `activity_clubs` relation and include the required fields `title`, `starts_at`, `ends_at`, and the current user as `creator`.
4. WHEN a Club_Owner_Role user creates a club event, THE Content_Service SHALL set the initial `event_status` to "Pending Approval".
5. IF the submitted `ends_at` value is equal to or earlier than the `starts_at` value, THEN THE Content_Service SHALL reject the request and return an API_Error indicating that the event end time must be after the start time.
6. IF the Strapi_REST_API returns a 400 status due to missing required fields or invalid data, THEN THE Content_Service SHALL return an API_Error containing the validation details from the server response.
7. IF the user does not have Student_Role or Club_Owner_Role, THEN THE Frontend SHALL prevent the event creation action from being available in the UI.

### Requirement 14: Event Approval by Ambassadors

**User Story:** As an ambassador, I want to review and approve or deny event creation requests, so that I can ensure events are appropriate and properly planned.

#### Acceptance Criteria

1. WHEN a user with Ambassador_Role requests pending events, THE Content_Service SHALL fetch events filtered by `event_status=Pending Approval` from the Strapi_REST_API with populated `creator`, `location`, and `activity_clubs` relations.
2. WHEN an ambassador approves an event, THE Content_Service SHALL send a PUT request to the event's `documentId` endpoint updating the event's `event_status` to "Scheduled".
3. WHEN an ambassador denies an event, THE Content_Service SHALL send a PUT request to the event's `documentId` endpoint updating the event's `event_status` to "Denied".
4. IF the user does not have Ambassador_Role, THEN THE Frontend SHALL not display the event approval interface.
5. IF the PUT request to approve or deny an event fails with a 4xx or 5xx status, THEN THE Content_Service SHALL return an API_Error and THE Frontend SHALL display an error message indicating the status update failed while preserving the current event list state.
6. IF the event's `event_status` is no longer "Pending Approval" when the ambassador attempts to approve or deny it, THEN THE Content_Service SHALL return the error from the Strapi_REST_API and THE Frontend SHALL display a message indicating the event has already been processed and refresh the pending events list.
